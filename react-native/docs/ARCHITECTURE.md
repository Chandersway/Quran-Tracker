# Architecture and contribution guide

The Kotlin application remains the functional specification. `source-catalog.json` and its provenance preserve curated copy; source acquisition/import scripts remain unchanged. The feature inventory is a release gate, not a substitute for implementing gaps.

## Module boundaries

- `src/domain`: pure rules and calculations. Keep React, storage, network and notification calls out of these files. Tests exercise compatibility-sensitive behavior here.
- `src/state`: typed local models, a pure reducer, hydration, serialized persistence, and read-only migration of old Android data. Side effects belong in adapters or coordinators.
- `src/content`: immutable Quran data and source metadata. Text/translations are immediately available; study and reciter catalogs load from bundled local assets. Run `npm run content:generate` to regenerate without editing source content.
- `src/services`: network, audio, secure session storage and notification adapters. Supabase auth/groups retain the existing auth, RPC, table and storage contracts. Personal notes, plans, history and progress stay local, matching Kotlin; there are no invented remote tables.
- `src/services/mushaf`: original formats/storage and an observable manager. Native `backgroundManager.ts` observes Android DownloadManager/JobService or iOS background URLSession through `background.native.ts`; JavaScript timers observe status, never perform native transfers. Web retains its own adapter. Unmounting does not cancel work; cancellation is explicit. Estimates require a known total and recent progress. Native lifecycle setup and limits are in [the background plugin](../plugins/backgroundMushafDownloads/README.md).
- `src/features`: screens and small feature-specific helpers. A screen coordinates a task using domain rules and services. It must show actual loading, empty and failure states and preserve the user's work.
- `src/shared` and `src/i18n`: shared accessible primitives, visual tokens, and provenance-backed curated messages. `T`/`AppText` renders strings literally by default; translate interface messages explicitly and substitute arguments into complete sentences.

## Reader interaction contracts

`src/features/quran/components/MushafFooter.tsx` owns the shared reader controls and reusable `MushafPageRail`; `mushafScrubber.ts` maps physical rail coordinates and tick ranges to exact pages. Page one is physically on the right, independent of the UI language. Dragging previews locally with a signed delta from the starting page, commits on release, and discards the preview on cancellation. Arrow buttons advance one page; book gestures retain spread-based turns. The page index opens the jump control; the lower row exposes zoom and explicit reading registration. Footer and menu actions receive the same `readingSessionId`, preventing duplicate page records within that reader session. Contextual plan/target completion remains a separate menu action.

The main Unicode/image reader retains footer, zoom, page rail, selection control and explicit registration in fullscreen. Short landscape uses compact toolbar/footer rows. Landscape, zoom and Warsh reserve the vertical-rail gutter before loading, in normal and fullscreen modes. A fit rail is inactive and does not intercept source text. Portrait-fit Hafs keeps full width and native scrolling for unexpected expansion; measurement cannot narrow the page after loading. Page/content measurements are keyed by edition/page/zoom/width/spread, and source-relative anchors preserve the reading point across viewport/fullscreen changes. `AppChromeContext` follows focused fullscreen and short-landscape readers, including text mode; blur/unmount restores global chrome. Edition replacement passes current selection/fullscreen state. Keep controls outside source text. The PDF reader has a compact landscape footer but no fullscreen mode. Device results belong to [native QA](NATIVE_QA.md), not these source contracts.

The footer's `getTickMetrics(firstPage, lastPage)` accepts density and whole-range read state. `content/mushafPageMetrics.ts` supplies edition-specific density; grouped ticks average their own pages. `features/quran/model/readPageMetrics.ts` derives read state from explicit history. A page registration proves only that exact page in that edition, never a continued ayah on an adjacent/different page. Whole known passages can cover verified ranges; any unmapped page keeps its aggregate neutral. Opening, scrolling and scrubbing never record reading. [Page metrics](MUSHAF_PAGE_METRICS.md) distinguishes density profiles, physical/printed offsets and remaining visual acceptance.

`SelectableMushafPage.tsx` renders one continuous Unicode buffer with exact offsets. Native Hafs stays hidden/noninteractive during fit measurement, then reveals a verified fit or explicit expanded fallback. Browser and native Warsh use expanded rendering: reconstructed Warsh lines are not exact scan geometry. Data, source font readiness and layout identity remain edition/page-specific. Preserve complete text and native selection. Verified Hafs words expose contextual glosses and enter the separately sourced Lexicon route; no Warsh-to-Hafs lexical mapping is guessed. Scan/PDF surfaces stay separate and have no verified selectable text layer.

`src/services/mushaf/selectableMushaf.ts` selects providers and owns an eight-page edition-keyed session cache. Warsh reads 604 local assets through `warshOffline.ts`; `warshMushaf.ts` uses the same verified network source only if a local asset is unavailable/invalid. Every page keeps exact source extent, numbering, word order and codepoints, including continued ayahs and original basmallah. `scripts/prepare-reader-assets.ts` validates the entire response before replacing page assets. Source/font provenance is in [Warsh Unicode](WARSH_UNICODE_SOURCE.md). Opening this representation is explicit and keeps edition/page/fullscreen context. Representation changes still reset zoom/vertical position; rotation/fullscreen within the same representation uses source-relative restoration.

`mushafTextGestures.ts` owns the shared swipe policy for text and printed pages: DOWN bounds identify the originating page edge, speed widens the allowed edge region, and displacement/straightness checks reject wandering gestures. Longer edge pans require prompt movement; vertical turns require the relevant scroll edge at DOWN. The passive Android observer uses protocol 3, supplying motion measurements and native selection state to this classifier. Prompt movement cancels the TextView's pending long press; stationary holds, existing selections and selection-handle dragging remain protected. A mismatched native protocol retains explicit page controls rather than invoking the older observer contract.

The explicit Browse/Select control separates page gestures from native text selection. Select enables the continuous selection buffer and disables page swipes and nested word presses. Browse disables native selection and restores word actions. Android Browse also classifies raw page-level touch releases, because a nonselectable TextView does not reliably supply the passive observer's complete stream.

Android swipe callbacks queue through `mushafPageTurn.ts`: raw JS END/Cancel must release the word responder before a microtask changes the page and unmounts its Text. A single gesture can commit only once even if raw and native callbacks both arrive. Dispose queued turns on unmount. Navigating immediately from native UP can strand React Native's responder and break the next page's word taps. The Android observer requires prebuild and a rebuilt native binary as described below. There is no equivalent iOS observer yet; native iOS gestures remain unverified and explicit page controls are available.

`src/content/hizb.ts` resolves Hizb openings from the same bundled division rows used by navigation. `HizbOpeningPreview.tsx` shares the opening-surah title, Arabic opening ayah and independently expandable translation across catalog/progress rows. NL/EN previews use `translations.ts` and the unchanged bundled source text; no runtime translation or invented canonical Hizb names are introduced.

The PDF runtime is pinned to `react-native-pdf` **7.0.5**. `plugins/withPdfRuntime.js` applies the tracked Android adapter in `plugins/pdfRuntime/patchPdf.js` during prebuild. Version and source fingerprints make it idempotent and reject partial patches or unexpected dependency changes; review the adapter before upgrading. `pdfZoom.ts` clamps the shared 1–3× zoom state, synchronizing footer steps and native scale reports. The adapter applies live zoom/page changes without rebuilding the document for each update, while structural configuration changes use a coalesced reload. Plugin changes require a rebuilt native binary.

## Adding or changing behavior

1. Find the source Kotlin screen, repository, and tests. Record the contract and curated message key.
2. Change the pure rule or provider interface first when behavior crosses screens. Keep platform-specific code behind `.native.ts`/`.web.ts` adapters.
3. Implement a complete user flow, including failure recovery. Preserve export schemas, Quran references and existing local data.
4. Run `npm run format` and `npm run verify`. Formatting is pinned and excludes generated Quran data; `npm run format:check` checks authored TypeScript and JavaScript without modifying files. For native modules or configuration changes, rerun `npm run android:local`; ordinary TS/JS changes use Fast Refresh.
5. Verify the actual screen on the emulator. Update the feature ledger with evidence and remaining external checks.

The Android selectable-book gesture observer is generated by `plugins/withMushafTextGestures.js` from its Kotlin source under `plugins/mushafTextGestures/`. It observes the existing native text/scroll views, checks the native selection before touch handling, and returns events without consuming touch input. Changes to this observer require prebuild and a new native binary; Metro refresh alone cannot install it. Keep native selection/handle dragging and vertical scrolling in the acceptance checks whenever changing page gestures.

## Security and portability

Production connection values originate in GitHub Secrets. The release workflow forwards required build configuration into EAS; server credentials stay in server secret stores. `EXPO_PUBLIC_*` values are extractable from a mobile binary, so only public endpoints and anon/publishable keys may be compiled. Native auth sessions are stored through Keychain/Keystore; local practice data is device-owned.

Supabase can later be self-hosted on a VPS while keeping the same Auth/PostgREST/Storage contracts. Audio uses stable object paths and a configurable origin, so moving the static mirror does not require changes to reader screens. A different backend requires adapter work: the current backend implementation and some service contracts remain Supabase-specific. Moving to an arbitrary VPS backend is not just a URL change.

## Implemented structure and remaining work

The application shell is now composed by `App.tsx`, `src/app/providers/AppProviders.tsx`, and `src/app/navigation`. The visible dashboard is `features/home/screens/MainScreen.tsx`; it uses `features/practice/components/ReadingStatisticsOverview.tsx` and `features/planning/components/ReadingPlanHomeCard.tsx`, rather than importing other screens. The onboarding flow likewise lives in `features/onboarding/components/OnboardingFlow.tsx` and is composed by its route and Settings.

Feature folders group screens, feature-owned components, and, where useful, hooks or providers. Shared visual primitives are named modules under `shared/components`, with palette and fonts under `shared/theme`. Services are grouped by capability. `content/mushafGeometry.ts`, `services/notifications/pushDevice.ts`, and `domain/onboarding.ts` now own the formerly feature-bound helpers; `domain/localDate.ts` owns the local calendar helper. Domain and services should not depend on feature UI, and one screen should not import another screen. Feature components can be reused across features when their ownership is explicit.

The persisted-state decoder validates supported records before exposing them to screens and retains unreadable source data for recovery. `T`/`AppText` is literal by default. Older string props on buttons, notices, fields and other shared primitives still translate keys/known aliases for compatibility; `Row`, `Sheet` and `Segments` provide explicit opt-outs for user-owned labels. These APIs have not all migrated to semantic-key-only props. These changes preserve source messages, route identifiers, import formats, and data contracts; they do not establish native parity on their own.

The notes screen now composes editor/filter hooks and dedicated editor, row and filter components; its curated copy lives in `i18n/notes.ts`, with platform sharing in `services/storage`. Account/profile operations use provider-neutral auth/profile contracts, and the raw Supabase client is no longer public on `Backend`. Profile name changes do not write the avatar column, so a slow profile load cannot erase the stored photo. The library and book reader have distinct screen files; theme colors, fonts and spacing have named modules.

Some screens remain large and combine presentation and coordination, including reader and account flows. Further extraction should follow cohesive responsibilities and preserve error recovery. The shared store still provides broad state through one context and serializes full state on committed changes; this can cause unnecessary rendering or writes, but no performance regression has been measured here. Measure real flows before changing subscription or persistence design, and preserve final-state durability, import ordering, and account ownership. Some screen-local copy and provider-specific contracts also remain; replacing the backend still requires adapter work.

See the [source directory guide](../src/README.md) and each feature's README for actual entry points. Route names, deep links, source provenance and existing local data are compatibility contracts, not folder names.

## F26 source modules

`home/screens/MainScreen.tsx` composes compact Today/Resume/Planning components and the same distribution summary used by detailed statistics. Quantities, registration counts, daily goal, independent plan and Hifz remain distinct. `home/model/resumeReference.ts` refuses a canonical caption for an unmapped page.

`study/screens/StudySourcesScreen.tsx` keys `StudySourceContent` by route identity. `services/study/studyRequest.ts` binds immutable source/reference requests, fixed trusted mappings and cancellation/generation checks. Missing Asbab coverage remains missing; contextual Irab uses original Quranpedia excerpts/citations.

`features/lexicon` owns routes/UI; `services/lexicon` owns exact QAC lookup and the separate Lane root-article provider. Only verified selected text enters canonical lookup; occurrences explicitly open Hafs. 346 roots have no exact Lane heading join and remain unmapped. `services/storage/readOnlyAssetDatabase.ts` imports native databases directly into hash-versioned `read-only-content`, validates metadata and enables query-only SQLite. Failed initialization removes only its own content copy. Web uses a separate memory database; user data is not overwritten.

`services/groups` owns account/group-scoped in-process drafts, keyset feed pages, separate pins, subscriptions and polling recovery. Backend ports hide Supabase details. Realtime publication is prepared, not deployed; INSERT/UPDATE invalidations complement polling, while deletion/visibility recovery waits for authorized refresh. Drafts do not survive process termination and no delivered/read receipt is invented.

[IMPLEMENTATION_F26](IMPLEMENTATION_F26.md) links source corrections and regression contracts. The inventory generator consumes `data/feature-evidence-f26.json`, rejects missing paths/symbols and separates implementation from native acceptance. Inventory hashes prove source coverage, not a parity percentage.

## Honest validation limits

Compilation does not establish functional parity. Windows supports the verified Android emulator and native build; native iOS execution requires macOS/Xcode or a device. Real authentication, group authorization, cloud storage and push delivery require configured accounts and have separate acceptance checks.
