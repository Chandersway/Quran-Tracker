3. Open the downloaded IndoPak PDF using the preserved `.tooling/indopak-primary-research.pdf` fixture (51,351,963 bytes, 612 pages). Verify first preparation, cropped margins, page 73 at zoom 2.25, exit/reopen cache reuse, cancellation/back, and immediate original fallback. Repeat with Arabic interface direction. Observe process memory on the actual emulator/device.
4. Check online Asbab index discovery and one indexed excerpt, tafsir/iʿrab requests, and native book database startup. Offline handler tests do not establish remote provider availability.

PDF preparation serializes uncached work so rapid reopen cannot allocate two books concurrently. The Android native worker opens a separate Pdfium document and streams its output to a unique temporary cache file; the JavaScript caller does not read or write PDF byte buffers on that path. The caller waits for a nonempty, closed output and for Expo's asynchronous move before returning the cache URI. Cleanup retains the original temporary URI because Expo mutates the moved File object's URI. Worker errors propagate to the existing retry/original controls rather than silently starting JS conversion. Native cancellation waits for the worker to settle before cleaning its output.

A versioned cache avoids future conversion. Without an installed native worker, a soft **32 MiB** budget opens larger uncached originals immediately, with optional crop preparation in the menu; this includes older Android shells and iOS. Native availability is based on the loaded module, not the Android platform name. The native path can automatically prepare larger books, including the 51.35 MB fixture. The fallback parses/saves in batches of 100 objects and yields every 50 page-box updates. It does not block reading larger books. Any preparation failure retains an original-file action; native crop-decode failure falls back to the original. The uncropped state is identified in UI.

The previous 25-object fallback produced approximately 746 timer handoffs on the 51.35 MB fixture (7,992 indirect objects, 612 pages). Root's device QA reported approximately 120–180 seconds of first preparation, prompting the native path and smaller automatic JS budget. A desktop comparison of the current 100-object/50-page fallback took 3,300 ms with 207 timer handoffs, process RSS of 265 MiB, and a worst 10 ms interval-probe gap of 202 ms; see `.tooling/parity-reader-batch-probe.ts`. These desktop figures do not establish native speed or memory safety. JS parse/save cancellation still waits for the current library operation; large documents no longer enter that path automatically without the native worker. Final rebuilt-shell timing, cancellation, original-file hash preservation and cache reopening remain device acceptance checks.

The PDF manipulation uses the documented [PDFPage crop/media boxes](https://pdf-lib.js.org/docs/api/classes/pdfpage) and [PDFDocument load/save options](https://pdf-lib.js.org/docs/api/classes/pdfdocument), without rasterizing Quran pages.
