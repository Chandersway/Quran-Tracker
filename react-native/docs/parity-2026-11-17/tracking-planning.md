## Strongest confirmed behavioral differences

### A. High: same content/day cannot be planned for different intentions

`R/features/planning/screens/PlanningScreen.tsx:103` considers `goalId` part of duplicate identity. Thus reading Hizb 1 and memorizing Hizb 1 on the same date pass its guard. The reducer’s actual dedupe key at `R/state/reducer.ts:392` and `:396` omits `goalId`, so it discards the second plan. The UI then closes and displays `planning.saved` at `PlanningScreen.tsx:143`. The Goals scheduling route also reaches this reducer (`R/features/practice/screens/GoalsScreen.tsx:129`).

Kotlin `K/data/GoalRepository.kt:154` inserts a plan carrying the goal ID and does not collapse independent intentions this way. The synthetic probe called the real reducer with goal IDs `[1,2,3]`; only `[1]` remained. This is not an untested visual assumption.

Existing `tests/agenda.test.ts:70` checks linking an existing plan once, and `tests/goals.test.ts:6` checks independent progress actions. Neither checks adding the same partition/date under multiple goal IDs.

### B. High: noon timestamps cause independent-plan undercount and wrong chronology

Both fresh and linked goal registrations assign `new Date(\`${date}T12:00:00\`).getTime()` at `R/features/practice/screens/GoalsScreen.tsx:110` and `:161`. Kotlin `K/data/GoalRepository.kt:144` combines the selected date with `LocalTime.now()`. The independent plan intentionally filters `timestamp >= started` in both source (`K/ui/ReadingPlanScreen.kt:38`) and RN (`R/domain/readingPlan.ts:23`).

Reproduced with real reducer/domain functions: plan starts at 14:00, goal record happens at 18:00, RN stores it at 12:00, and `readingPlanLogged` returns **0 Hizb**. Giving the otherwise identical registration its actual 18:00 timestamp returns **1 Hizb**. Noon also makes all same-day goal entries share an artificial time in newest-first detail lists. Daily goals still count the entry by `dateKey`, so this is specifically timestamp-dependent consumers, not universal data loss.

`tests/reading-plan.test.ts:32` verifies an already-correct entry’s timestamp cutoff, not the GoalsScreen producer. `tests/agenda.test.ts:70` supplies fixture timestamps and likewise misses the producer error.

### C. High: quick check-in success is not tied to persistence or one submission

Kotlin keeps one request ID for an open dialog (`K/ui/DashboardScreen.kt:119`), locks submission while saving (`:1110`), calls success only after the repository transaction (`K/viewmodel/QuranViewModel.kt:16`), and renders failure/retry without closing (`K/ui/DashboardScreen.kt:1109`). The transaction records a durable request key (`K/data/QuranProgressRepository.kt:53`, `:68`).

RN creates a new ID inside every `save()` call, dispatches each target, then closes (`R/features/practice/components/QuickCheckInSheet.tsx:59`). Its only disabled condition is invalid draft (`:209`). `R/state/store.tsx:134` later writes AsyncStorage in an effect and reports failure globally; there is no Promise/acknowledgment exposed to this sheet. An accidental second handler invocation creates a different ID and counts again. A failed write is only discovered after the sheet has closed. The bulk Practice action even displays `quickCheck.saved` immediately (`R/features/practice/screens/ProgressScreen.tsx:65`).

Same-request-ID dedupe is present at `R/state/reducer.ts:139`; it is insufficient to prove this UI workflow. This is a traced implementation gap, not a claim of having physically double-tapped or forced an AsyncStorage failure.

### D. Medium: reading changes Hifz assessment age

Kotlin read updates use `existing.copy(isRead=..., readCount=...)` and leave `lastUpdated` untouched: `K/data/QuranProgressRepository.kt:94` and `:192`. Hifz writes explicitly set it at `:238`. Review advice uses that timestamp (`K/ui/DashboardScreen.kt:2035`).

RN check-in overwrites `lastUpdated` at `R/state/reducer.ts:171`, including an already-assessed Surah/Juz. `R/domain/hifz.ts:25` interprets the field as `assessedAt`, and `:31` drives the Home review queue (`R/features/home/components/PracticeOverview.tsx:71`). The probe confirmed that a Surah score of 30 assessed three days earlier stays **30**, but a plain reading changes its review advice from **2 days overdue** to **due in 1 day**. Numeric score preservation alone is not complete independence.

### E. Medium: missing or changed tracking interactions

- **Re-read dialog:** Surah is implemented through `R/features/quran/screens/QuranScreen.tsx:120` → `SurahActionsSheet.tsx:38`. For Juz/Rub, the active Practice route (`R/app/navigation/MainTabs.tsx:18`, `:26`) instead uses a selected-items list and bottom actions (`R/features/practice/screens/ProgressScreen.tsx:157`, `:211`). Existing counts are shown in rows, but selecting an already-read item does not display the source repeat/count/remove/cancel dialog. New registrations and removal still work.
- **Hifz entry gesture:** Kotlin long-press opens the score editor for Surah/Juz/Hizb (`K/ui/SurahScreen.kt:335`, `K/ui/JuzzScreen.kt:278`, `K/ui/HizbScreen.kt:247`). RN Surah long-press opens a combined action sheet containing its score editor; Juz/Hizb use `bar-chart` buttons (`R/features/practice/screens/ProgressScreen.tsx:192`) and have no long-press handler.
- **Hifz tint preference:** Source preference is read/persisted at `K/MainActivity.kt:115`, `:211` and exposed at `K/ui/HamburgerMenu.kt:493`. Source card styles consume it at `K/ui/SurahScreen.kt:321`, `K/ui/JuzzScreen.kt:252`, `K/ui/HizbScreen.kt:214`. RN only preserves the legacy key in `R/migration/legacyRoom.ts:109`; no active preference or card styling consumes it. Home’s few score colors (`R/features/home/components/PracticeOverview.tsx:181`) do not implement the preference.

### F. Medium: weekly activity uses a different population

Source active Stats gets `viewModel.dayActivity` (`K/ui/StatsScreen.kt:157`), whose DAO groups **all actions** after the rolling seven-day cutoff (`K/data/ReadingHistory.kt:85`; cutoff `K/viewmodel/QuranViewModel.kt:58`). RN builds seven calendar-day bars with `row.action === 'read'` (`R/features/practice/components/ReadingStatisticsOverview.tsx:152`). Hifz/review registrations consequently disappear from RN activity even though they appear in history. The date window also differs slightly: rolling seven-day cutoff versus seven calendar dates. Ring counts intentionally remain reading-only in both implementations; that is a separate and correct rule.

### G. Intentional fullscreen exception: floating Focus timer

Kotlin draws the timer whenever running or partially elapsed/paused (`K/MainActivity.kt:882`), including the reader. RN’s global mount is conditional on `!immersiveReader` (`R/app/navigation/AppNavigator.tsx:249`). Mushaf sets that flag for fullscreen or short landscape (`R/features/quran/screens/MushafScreen.tsx:230`), as do downloaded PDF (`R/features/quran/components/DownloadedPdfMushaf.native.tsx:67`) and text reader (`R/features/quran/screens/ReaderScreen.tsx:258`). The timer continues in its provider. The user later expressly requested fullscreen Mushaf “zonder dat je een hele interface ziet behalve eventuele transparante slider.” That user intent overrides exact Kotlin overlay parity. Treat suppression in fullscreen as intentional, not a confirmed missing-feature bug; short-landscape suppression is a related design difference. The floating display remains mounted on ordinary routes outside Focus (`R/features/practice/providers/FocusProvider.tsx:121`).

### H. Medium: Agenda reminder presets and completion behavior

Source reminder dialog provides Now, +30 minutes, Tonight (20:00) at `K/ui/AgendaScreen.kt:62`. RN’s active sheet at `R/features/planning/screens/PlanningScreen.tsx:560` only offers hour/minute fields, Save and Clear; the presets are absent.

Source direct completion clears saved reminder fields and cancels its schedule at `K/data/PlanningRepository.kt:126`. RN direct completion updates only `isDone/historyLogged` (`R/state/reducer.ts:207`). **This does not mean a completed item still fires:** `R/services/notifications/planningReminders.ts:79` excludes done items, and the mounted coordinator reconciles on plan changes (`R/features/planning/components/PlanningReminderCoordinator.tsx:24`). The confirmed difference is retaining the time and automatically making it eligible again when the item is undone before the due time. The synthetic real-domain probe produced 0 desired reminders while done and 1 after undo. Goal-linked completion separately clears reminder fields correctly (`R/domain/goals.ts:66`), covered by `tests/agenda.test.ts:70`.

## Present behavior and source clarifications

### Section 4: preserve the real removal contract

Do not characterize source removal as “undo only the last registration.” Kotlin Surah/Juz removal clears the whole read mark/count but **retains history** (`K/data/QuranProgressRepository.kt:114`, `:219`). Rub removal resets the row and deletes **all of today’s matching quarter-name history rows**, while retaining other dates (`:165`; SQL `K/data/ReadingHistory.kt:98`). RN matches these semantics in `R/domain/progressActions.ts:29` and `:36`.

The local Kotlin Hizb tracking page exposes **four Rub buttons** (`K/ui/HizbScreen.kt:315`), each opening its own count/repeat/remove dialog. It does not expose a separate full-Hizb three-action dialog. Full-Hizb registration is the quick-check path. RN offers an additional batch whole-Hizb action whose visible read count is the minimum of four Rub counts (`R/features/practice/screens/ProgressScreen.tsx:125`). That derived progress count must not be confused with the full-Hizb registration chart.

Reader page checkbox toggle is a separate, explicitly requested behavior: `R/features/quran/components/MushafReadingActions.tsx:51` → `mushaf/readMark`. This report does not count it as a re-read regression. The optional reader target registration (`MushafReadingActions.tsx:121`) has a simple confirm and per-session ID; it does not supply the missing tracking dialogs.

### Section 5: numeric score behavior is present

`R/state/reducer.ts:295` permits only 114 Surahs, 60 Hizbs and 30 Juz; Rub has limit 0 and is rejected. Writes round/clamp to 0–100, set `hasHifzScore = score > 0`, preserve prior mark/count fields, and do not write history. `R/domain/hifz.ts:11` excludes zero/unassessed values. The score slider, numeric input, clear and save are active in `ProgressScreen.tsx:274` and `SurahActionsSheet.tsx:104`. Home range application normalizes endpoints and dispatches one independent score per chosen row (`PracticeOverview.tsx:77`, `:292`), matching source range semantics (`K/data/QuranProgressRepository.kt:249`).

Home RN shows the average of the currently selected score category (`PracticeOverview.tsx:60`). Kotlin Home calculates a combined average of assessed Surah/Hizb/Juz items (`K/ui/DashboardScreen.kt:1997`). Both exclude zero; Stats mastery remains the required Hizb-only mean in both. This is an aggregation presentation difference, not a missing Hifz feature.

### Sections 6–7: full Hizb registration and chart are separate from Rub completion

Full-Hizb quick-check creates one history row per selected Hizb and updates its four Rub marks in both implementations (`K/data/QuranProgressRepository.kt:61`; `R/state/reducer.ts:157`). It deliberately does **not** create a Hizb read-progress row; a pre-existing Hizb Hifz row stays intact. Marking four individual Rubs does not create a full-Hizb history entry and does not increase this chart.

Strictly, the source chart contract is `action='read' AND type='hizb'`, correct owner/time/id, `COUNT(*)` (`K/data/ReadingHistory.kt:27`); it does not inspect the source key or reject a legacy quarter name. RN ports that predicate (`R/domain/hizbAnalytics.ts:59`). Thus “only explicit whole-Hizb quick-checks” is stronger than what either generic history predicate proves for arbitrary imported/legacy rows. The important normal-flow distinction—no four-Rub aggregation—is present.

Zero counts are in the data for all 60 IDs (`K/data/HizbAnalytics.kt:14`; `R/domain/hizbAnalytics.ts:41`). When some readings exist, zero-height/minimum-height bars remain selectable. When all are zero, both show an empty message (`K/ui/HizbOverviewCard.kt:63`; `R/features/home/components/HizbOverviewCard.tsx:68`), so this is a source-versus-request clarification rather than an RN-only regression.

RN maps blank owner IDs to guest (`R/domain/hizbAnalytics.ts:60`); Kotlin’s SQL uses exact equality, with signed-out owner `guest` (`K/data/HizbAnalytics.kt:18`). The RN test explicitly expects blank-owner RN guest records to count (`tests/hizb-analytics.test.ts:54`). Treat that as a deliberate compatibility rule requiring import-policy review, not silently identical SQL.

### Section 8: existing rings are substantial implementations

The same filtered records drive segments, legends, detail counts and newest-first rows (`R/domain/statistics.ts:12`, `:27`, `:34`; `R/features/practice/components/ReadingStatisticsOverview.tsx:127`). Rings count registrations, **not `amount` and not Quran completions**. Detail rows show the quantity separately (`ReadingStatisticsOverview.tsx:203`). Source non-type distributions and RN both restrict to top eight buckets (`K/ui/StatsDrilldown.kt:36`; `R/domain/statistics.ts:51`); “all” in such a detail means all displayed distribution buckets, not every historical partition beyond the top eight.

Named references and exact partition ranges use canonical mappings (`R/domain/statistics.ts:85`; `ReadingStatisticsOverview.tsx:158`), and Hizb/Rub opening previews use the first four words of the Hizb opening (`R/domain/statistics.ts:299`), as source does (`K/ui/StatsScreen.kt:953`). Generic ambiguous amounts do not fabricate exact ranges. The complete day/week/month history grouping is separately implemented (`R/features/practice/components/StatisticsHistory.tsx:21`) and preserves all action types. Legacy quarter-group collapsing there does not change ring membership/counts.

Mastery is the floored average of positively assessed Hizbs and shows the assessed count out of 60 (`ReadingStatisticsOverview.tsx:144`, `:557`; source `K/ui/StatsScreen.kt:282`). Streak uses reading or memorization, including yesterday when today has no activity (`R/domain/statistics.ts:251`; source `K/data/ReadingStatsSummary.kt:70`). Summary points/quantities and Home motivation are implemented, with pure-domain tests at `tests/statistics.test.ts:253` and `tests/hifz-motivation.test.ts:52`.

Reset is confirmed by the native alert call (`ReadingStatisticsOverview.tsx:224`) and clears history/read flags/counts while preserving scores, memorized flags, goals/plans/preferences (`R/state/reducer.ts:464`). Source also clears its durable request table (`K/data/QuranProgressRepository.kt:257`). RN also clears imported request IDs, but active quick-check dedupe otherwise relies on retained history rows. No alert or failed durable-reset workflow was device-tested.

### Section 9: checklist state is independent

Both implementations use one set of canonical ayah indices for all four partitions, rather than independent booleans (`K/data/ReadingChecklist.kt:20`; `R/domain/checklist.ts:27`). Full/partial render state is recalculated from that set (`ChecklistScreen.tsx:161`). Checking updates coverage only (`:183`); Stop updates position only (`:213`); Continue uses the first ayah after the saved partition (`:89`); opening a row uses its first ayah (`:199`). Separate resets preserve the other field (`R/domain/checklist.ts:84`). The screen writes only its checklist sidecar (`ChecklistScreen.tsx:21`, `:69`) and never dispatches history actions. There is load/save failure handling and retry, but only source inspection establishes those UI paths here.

### Section 10: focus mechanics are present

`R/domain/focus.ts:33` prevents intention/duration changes while running, clamps custom minutes, uses a deadline for elapsed time, supports pause/resume/reset, and reports finished. The screen offers all four presets and intentions and opens the current Mushaf cursor (`FocusScreen.tsx:173`). Provider samples on foreground (`FocusProvider.tsx:94`), persists state transitions (`:77`), and stores a completed focus session once by ID (`:103`, reducer `R/state/reducer.ts:452`). Kotlin’s timer is a MainActivity one-second coroutine decrement (`K/MainActivity.kt:397`); the RN persisted-deadline approach is an implementation improvement, but native lifecycle behavior remains unverified by this audit.

### Section 11: goals and journey are implemented, with a changed recording form

Goal IDs 1/2/3 map to read/memorized/review (`R/domain/planning.ts:14`). Progress filters date/action and converts units (`R/domain/goals.ts:26`); minutes are measured separately. Target snapshots and carried work are retained across edits (`:102`). Carry adds remainder to today, spread allocates it across today plus the next two days, skip adds none, and resolving twice is a no-op (`:147`), matching `K/data/GoalRepository.kt:170`.

The source active recording dialog chooses a Surah/Hizb/Juz and registers **one unit of that chosen content**, unless linked to a matching planned session (`K/ui/GoalHubPanel.kt:233`). RN adds a measured amount/unit form (`GoalsScreen.tsx:415`) and defaults that unit to the daily goal’s unit (`:198`). Example: for a pages goal, selecting a Surah and accepting defaults registers one page with Surah content identity, not one whole Surah as Kotlin does. This may be a useful capability, but it is not an exact port of the source registration semantics. Schedule still writes one selected partition in both.

Reading journey counts reading since its original start, includes repetitions, caps at one Quran and converts to 604 pages (`R/domain/readingJourney.ts:20`; source `K/ui/ReadingJourneyDialog.kt:33`). Its dynamic end follows current daily amount and progress (`R/domain/readingJourney.ts:38`; source `K/data/GoalRepository.kt:60`). Daily pages or inclusive finish-date selection updates the daily reading goal (`ReadingJourneyPanel.tsx:62`; source `K/ui/ReadingJourneyDialog.kt:87`). Agenda displays the three goals and links to their selected-date management (`PlanningScreen.tsx:280`). This is separate from generated Khatma agenda itineraries and from the independent reading plan.

### Sections 12–13: remaining plan/Agenda parity
