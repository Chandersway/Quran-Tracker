# Notification receiver parity

`index.ts` imports `groupPushTasks.native.ts` before React mounts. That module defines the native Expo background task and installs the foreground display handler. It does not request permission or register the device. The **Enable push on this device** action creates the channel, requests permission, retrieves the native FCM/APNs token, registers it with the existing backend, and registers the background task.

Android continues accepting the original FCM data-only shape: `kind=group_reply`, `event_id`, and `recipient`. No notification payload was added to the Android sender. The receiver checks the opted-in account, current session, OS permission and local quiet hours, then calls `get_group_push_target_v1` to resolve event ownership, active membership and published post access. It checks global reply preferences and per-group mute preferences, then rechecks the account and local preferences before showing the exact generic Kotlin notification text. Stable notification identifiers and a delivery cache deduplicate foreground/headless delivery.

Expo SDK 58 shows foreground notifications if a display handler times out. Group messages are therefore suppressed immediately; asynchronous authorization schedules a local notification only after validation. Malformed group messages remain suppressed. APNs alerts already displayed by iOS in the background are not displayed a second time by the task. Their server-side account/membership/preference checks remain necessary.

Notification taps resolve the event through the authenticated RPC again; notification-supplied group codes and URLs are ignored. Legacy `qurantracker://notification/group/<event-id>` links resolve through the same server gate. The selected discussion opens first in the group feed. Planning reminder taps look up the current local plan and open its exact reading range; deleted/completed plans do not open a stale target.

The token listener updates an existing opt-in after token rotation. App resume refreshes its language, timezone, permission and quiet-hour registration without asking for permission. A different signed-in account requires a fresh explicit opt-in. Sign-out, account deletion and device unregistration revoke the local account gate, dismiss group notifications, unregister the task/native push token, and attempt remote installation removal. Sign-out can still finish offline.

Android Firebase client configuration comes from `GOOGLE_SERVICES_JSON` when supplied as a local path or EAS file environment variable. Local development can reuse the existing ignored `app/google-services.json` from the Kotlin project. Its values are not copied into source files. APNs signing and the server's FCM service account remain server/build configuration, separate from public client configuration.

`group-push-policy.test.ts` covers provider envelopes, account changes during requests, event access, OS permission, category/group mutes and quiet-hour boundaries. `notification-destinations.test.ts` covers local plan destinations. Live FCM/APNs delivery requires platform credentials, an opted-in signed-in test device and an explicit test event; local policy tests do not write to the configured backend. As on the Kotlin app, Android force-stop and OS delivery restrictions can prevent background delivery. Quiet-hour registration is synchronized to the server so its delivery queue can defer sends; the local receiver suppresses arrivals during quiet hours.
