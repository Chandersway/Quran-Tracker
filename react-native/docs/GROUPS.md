# Groups implementation and verification

Groups is a primary navigation destination. Its overview lists the signed-in account's groups and searches that list. Invitations accepts a source-format group code or trusted native/HTTPS invitation link. Creation retains the source's three steps: basics, goal, and access/member permissions. Group detail opens the selected group's feed, with its name/logo and its own scoped posts. Account changes unmount private group state.

The detail screen composes separate feed, task, reading/ranking, member/access, media, event, notice, rules, profile, settings, moderation and audit panels. The typed `groupOperations` service calls the existing Kotlin RPC/storage contracts. Local permission checks control actions; Supabase authorization remains authoritative. Failures remain visible and retryable, rather than becoming successful empty responses.

The feed includes author avatars or initials, selected-locale timestamps, pinned posts, four reaction types, post editing/deletion/reporting, and collapsed comment threads. Per-post drafts survive closing a thread and failed submission. Comment deletion has a separate confirmation and restores the thread without discarding its draft. Notification post targets are filtered within the selected group's published posts.

Members supports existing custom roles, rank/owner/self restrictions, removal/blocking, invitation creation/revocation and access-request review. Other panels include private media upload/preview/share/delete with upload rollback, events and RSVP/status, task progress/status/points, exact member reading ranges and leaderboard periods, group-specific profiles/avatar/logo, active rules publication, notices/read state, report review and paginated audit.

Pending invitations persist across onboarding, authentication and process recreation. Joining/acceptance requires an explicit action. Only a plain-code `GROUP_INVITATION_REQUIRED` refusal offers an access request; invalid secure invitations and network failures do not. Links retain the original `qurantracker://group/CODE` and `https://qurantracker-8f775.web.app/group/CODE` hosts. The Android HTTPS intent filter requires rebuilding the native application.

The source has no public group-discovery RPC or leave-group operation; neither is fabricated here. Existing role assignment is supported; role-definition creation is not exposed by the source API. Rules retrieval returns the active version only, matching server RLS. Governance panel labels absent from Kotlin are explicitly identified as new functional copy requiring review in `src/i18n/new-ui-copy.json`.

Automated tests use fake RPC/storage ports and fabricated identifiers, covering exact group scoping and parameter names, cursor fields, invalid uploads/dates, upload rollback, signed-URL recovery, reading equivalents/ranges, trusted links and pending-invitation preservation. They make no production requests. TypeScript/lint checks cover the connected panels. Authenticated account, server-permission, real media-transfer and remote-push smoke tests remain separate acceptance work; a passing local suite does not establish those live results.
